## 0. 先说结论（一句话）

**轮换接口早就接上了，不是「没接」，真正缺的是「谁去查、什么时候查」。**
现行代码把「查地图」排在**最后**一道保险（只在总结页没读到地图时才查），而且默认**只查一次**；
改成「**开局那一下查到，就记为本局地图**」——`mixed_control` 的 4/4、`wildcard` 的 1/1 都是这么对上的。
再加一条**错图护栏**，让接口数据旧了也不会写错图。

### 1.2 实测：它其实能推得挺准

用**你本机**配对令牌拉了一份真实响应，拿你库里**已经有地图**的 14 局做对照（开局时刻按现行公式「结束 − 存活 − 60 秒」）：

|---|---|---|

也就是说：**近期、窗口内的局，它就是对的；推不出来时它就沉默，不会瞎写。** 这套地基是好的。

### 1.3 但它在你的库里**从来没生效过**

- `matches` 表 24 局：`map` 有值 14 局、空 10 局；`started_at` **0 局**（一局都没写进去）

  但**从来没有**「第 N 局地图推出来」或「没读到地图，按时间推」的行 → `guess()` 一次都没跑过
- 原因就在第 1.4 节

### 1.4 真正卡住的 4 个地方

**① 触发条件太窄 —— 这是最致命的一条**

```python
# map_guess.py:254
if row is None or row["map"]:
    return                   # 上游自己读到了，不动
```

上游其实**几乎每次都能读到地图**：14/14 有地图的局里，`mode` 为空的 5 局**也**有地图
（说明是开局横幅那条路读到的）。所以「上游没读到地图」这个条件极少成立，
回推逻辑等于被整段绕过。你那 10 局没地图的，**恰好也是 `mode` 为空的那些**
（横幅没拍到 → 模式地图都没拿到 → 而我们又在等「有模式才查」→ 死锁）。**互锁**：

```
没地图 ← 因为没模式 ← 因为不查接口 ← 因为要先有地图才查
```

**② 只查一次，错过重试**

`_fill_saved` 只在 `on_summary_saved` 里跑一次。那一瞬间恰好：
- 接口超时 / 服务端在重新抓 `playlists_r5.txt`（`source` 字段会落到 manual YAML）；
- 或开局算出的时刻比服务端最新 `previous` 还早**几分钟**（窗口边界）；
- 或这时模式还没确定（`lobby_mode` 要回大厅才刷新）

→ 这次没查到，**就再也没有第二次**。我们实测时是「结算后几十秒查」，
而结算瞬间离你落地常常只有 2~4 分钟，正好卡在启动横幅刚结束、服务端还没轮转的缝里。

**③ 一场里只查一次，混战/外卡容易跨边界**

现行规则是「三个候选时刻必须算出同一张图才填」。
- 大逃杀 90 分钟一片、排位 270 分钟一片，这条规则没问题；
- 但**混战 15 分钟一片**，一局打到 10 分钟以上，候选必然跨片 → 必然「不填」。
  你的 `mixed_control`/`mixed_bullet_time` 局正是重灾区。
- 另外你库里两套命名并存：`哈蒙德实验室`（匹配）/`碎片镇`（混战 POI）。
  `config/match_start.json` 的已知地图只有「世界尽头/奥林匹斯/风暴点/诸王峡谷/破碎月亮/残月」——
  **混战 POI 名（碎片镇/哈蒙德实验室）不在名单里**，得先把这一套统一，否则回推出来的值会跟横幅读到的不是一回事。

**④ 一个只有 ApexPacks 能修的死结：`wildcard` 组整片消失**

`server/api/maprotation/index.get.ts:540-546`：活动带 `hideWildcard: true` 且在跑时，
**直接 `delete result.wildcard`**，活动（`event`）组本身也**没有 `upcoming`**（只有 `current`，一站就是半个月）。
于是活动期内 `evo.previous.wildcard` 也不存在 → `map_lookup` 里 `wildcard` 那个组**一片数据都没有**。

后果：活动期间你打外卡，接口**永远推不出地图**（我们交叉验证时 `wildcard` 只摊出 1 片，
还是活动那一张 `kings_canyon`，靠 `wildcard→event` 兜底才凑上）。

> 这条我在 `/maprotation` 里**没有**、也不打算乱改服务端行为——它是对的（外卡入口确实被活动顶掉了）。
> 但要给 Evo 用，**需要你在服务端多给一份「活动期内被顶掉的那组仍在跑什么」**（见第 4 节 P1）。

## 2. 目标（我认为对的语义，请你确认）

1. **默认地图 = 接口在开局那一刻说的那张**（仅限有配对、有网络、模式认识的局）
2. **横幅读到的地图/模式永远覆盖接口**（你 2026-10-24 已经定的口径，保持不变）
3. **接口数据可能旧 → 加护栏**：开局后「另一个来源」（横幅或你自己的对局时长倒推）若能证明结论不一致，就**不写**
4. 查不到、数据旧、模式不认识、没配对 → **一律留空**，绝不写错图（沿用现有原则）
5. 上游**一行不改**，全部走 `paimiao_cloud/` 注入（`AGENT_RULES.md` 第 7 条）

## 3. 我提议的改动（都在 `paimiao_cloud/`）

### 3.1 核心：把「查接口」的时机从「最后一道」提前到「开局那一下就查」

| 时机 | 做什么 | 改动 |
|---|---|---|
| 大厅读到模式后 / 开局横幅出现时（第一次） | `map_guess` 记下 `started`（已有），立即 `map_lookup.resolve(mode)`；把最近的轮换表缓存在内存（`CACHE_TTL` 300s 已够） | 扩 `map_guess._install_started_hook()`：记时刻的同时解析一遍 |
| 每局 0.3 秒的主循环里（`in_match` 判定中） | 记下**最后看到对局 HUD 的时刻**（约等于「自己被淘汰或夺冠那一刻」，比总结页结束时间准），以及对局 HUD 存活计时 | 新增轻量 hook，只在内存里加减，不读库、不联网 |
| `on_summary_saved` | 已有，但**去掉 `row["map"]` 短路**：改成「接口结论 vs 横幅结论」比一次，空才写 | 改 `_fill_saved` |
| `PostMatch.finish()`（收尾） | 已经有 `reset()` 在兜底，保留 | 不动 |
| 兜底重试 | 查不到时，把 `(match_id, 时刻, 模式)` 扔进一个内存队列，**每 60 秒最多重试 2 次**（总时长 5 分钟内），成功即写库并记日志 | 新增，约 40 行 |
| 历史补填 | 只处理「结束时间落在服务端能覆盖的窗口内」的局；查不到就跳过，不联网翻历史 | 新增，可选开关 |

### 3.2 护栏：什么时候**不写**接口的结论

只在能证明「接口数据旧了」时才拦：

- **横幅有地图** → 直接以横幅为准（不写接口，保持现状）
- **横幅有地图、接口结论不同** → 判接口数据旧，本次不写，记一行日志（用于统计误报率）
- **对局 HUD 实际时长** 能推出一段明确的开局区间，若服务端地图片的边界落在该区间**内部** → 说明这局跨了边界，不写
- **超过 90 分钟还查不到那片** → 不写

> 注意：**不能**用「结算时间 − 存活」去和接口比，因为现行公式里那句 `−60s` 本身就有偏差
> （我们实录里服务端 `remainingSecs` 和真实时间差几十秒量级；再叠上存活读数的误差，
> 边界附近容易误判）。所以护栏只用「横幅」「HUD 实测时长」两个硬来源。

### 3.3 模式优先级：`wildcard→event` 要收紧

现行 `MODE_GROUPS["wildcard"] = ("wildcard", "event")`。
活动跑半个月、`event` 片是 505 小时的超长窗口，`wildcard` 组一消失，
**所有外卡局都会被推成活动图**（宁可这是「碰巧对」，不能靠这个）。

改成：**只认 `wildcard` 组**；`event` 组仅在「我们确定这一局就是活动入口」时才用
——而那要靠 P1（服务端补数据）或用户在大厅看到的活动名，不靠猜。

> 副作用：活动期内外卡局会**留空**，而不是填活动图。我倾向于这个（第 4 条原则），但这是你的玩法，
> 你说了算（见第 7 节问题 ③）。

### 3.4 命名统一（必须一起做，否则推出来的值跟横幅对不上）

`config/match_start.json:16` 的已知地图：`世界尽头、奥林匹斯、风暴点、诸王峡谷、破碎月亮、残月`
但你库里实际存过：`碎片镇`、`哈蒙德实验室`（混战 POI）、`世界尽头`……

- 大逃杀/排位：`code → 中文名` 映射 `map_lookup._CODES` 已经齐全，**不用动**
- 混战：`mix_*` 的 code → POI 名（`碎片镇`/`哈蒙德实验室`…），需要把「POI 名」这套**写进 `config` 之外的一份本地映射**（我们自己在 `paimiao_cloud/` 里维护，不碰上游 `config/`），保证与横幅读数**逐字一致**
- 若某 code 认不出中文名 → **不写**（沿用 `map_lookup.map_name()` 返回 None 的规则）

### 3.5 要新加的东西 / 约定

| 项 | 内容 |
|---|---|
| 日志 | `[地图回推]` 前缀已有。新增两类：「第 N 局地图由接口定：X（模式/时刻/组）」「接口数据旧，未采用（横幅 X / 接口 Y）」——**这两行以后就是你验证 / 统计的唯一依据** |
| 开关 | 设置页加一个开关「用地图轮换接口补全地图」（默认开；关闭后行为与现在完全一致）。落在 `paimiao_cloud/cloud/state.py` 的 state 里，不动上游配置 |
| 请求量 | 每局最多 1 次（缓存 5 分钟内 0 次）；兜底重试最多 2 次 → **正常一天 30 局 ≈ 30 次请求**，对 ApexPacks 压力可忽略 |
| 隐私 | 请求只带配对令牌 + `User-Agent: EvoTracker/map-lookup`，不带任何对局信息 → 服务端无法从这次查询反推你的局 |

## 6. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 接口数据旧（YAML/抓取滞后） | 写错图 | 横幅护栏 + HUD 时长护栏；查不到就不写 |
| 活动期 `wildcard` 组缺失 | 外卡局留空 | P1 服务端补数据；没补上就留空，不填活动图 |
| 服务器抽风 / 超时 | 这一局地图空 | 已有缓存 + 重试 2 次；不影响记录本身（任何异常都吞掉） |
| 混战 15 分钟一片 | 边界局可能不填 | 用 HUD 实测时长定区间，区间内遇到片边界就放弃 |
| 命名不一致 | 面板/小程序筛选出两套图名 | 第 3.4 节统一映射；「认不出中文名就不写」 |
